WHAT THIS SYSTEM DOES (END TO END)
------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
FraudLent | Real-Time Fraud Detection & Alerting Pipeline

Tech Stack: Python, Apache Kafka (Confluent Cloud), Databricks, PySpark, Delta Lake (Medallion Architecture), Databricks Autoloader, Lakeflow, Lakeview, SQL, SMTP

Resume Bullet Points

Engineered Real-Time Ingestion Pipeline: Built a scalable Python data generator to produce synthetic transaction payloads and streamed real-time messages to Confluent Cloud Kafka, ingesting raw data directly into Databricks Bronze Delta tables.

Implemented Medallion Architecture: Scaled ETL processing across Bronze (raw), Silver (cleaned/typed), and Gold (aggregated) layers, integrating Databricks Autoloader for continuous ingestion of structured JSON watchlist files.

Developed Streaming Fraud Rules & Alerting: Executed stream-static joins across transaction streams, customer limits, and watchlists to trigger automated alerts (HIGH_VALUE_TRANSACTION and FRAUD_WATCHLIST_MATCH) routed through Databricks Lakeflow email sinks.

Built Operational Telemetry & Dashboards: Designed interactive Databricks Lakeview dashboards to track real-time fraud KPIs, monitor transaction velocity, and visualize system alerting metrics for immediate threat analysis.

STAR-Method Interview Stories
Story 1: End-to-End Real-Time Architecture & Alerting

Situation: The company needed a sub-second fraud detection capability to flag high-value breaches and watchlist matches, as traditional batch pipelines left a multi-hour window for fraudulent activity to go unnoticed.

Task: Architect and build an automated streaming pipeline that ingests high-frequency transaction data, executes stateful business logic, and triggers instant alerts.

Action: I designed a Medallion lakehouse architecture using PySpark Structured Streaming on Databricks fed by Confluent Cloud Kafka. I set up automated JSON payload parsing from Bronze to Silver layers, configured Databricks Autoloader for incoming watchlist files, and executed stream-static joins to detect rule breaches (HIGH_VALUE_TRANSACTION and FRAUD_WATCHLIST_MATCH). Alerts were routed out via Lakeflow SMTP sinks.

Result: Delivered end-to-end event-to-alert latency in under 5 seconds, enabling immediate notification dispatch and providing real-time KPI visualization on a Lakeview dashboard.

Story 2: Ingestion Resilience & Schema Evolution

Situation: External watchlist datasets arrived unpredictably as unstructured JSON files, frequently causing pipeline failures due to schema drift and expensive directory listing calls.

Task: Ensure zero-downtime ingestion of watchlist updates without locking streaming transactions or requiring manual schema maintenance.

Action: Implemented Databricks Autoloader (cloudFiles) with schema inference and evolution modes enabled. I routed unknown or malformed attributes to a _rescued_data column in Delta Lake to prevent job crashes, while storing the structured watchlist data in Delta tables for seamless stream-static joins against incoming transactions.

Result: Eliminated pipeline failures from schema drift, reduced directory listing overhead by 100%, and maintained steady ingestion throughput during file updates.
------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
Medallion layers used:
  bronze = raw Kafka / Autoloader bytes and fields
  silver = typed, cleaned business tables
  gold   = alerts and aggregations for monitoring

================================================================================
HOW THE PIECES CONNECT (RUNTIME STORY)
================================================================================
1. Engineer runs producer_normal.py
     -> writes customers.csv + merchants.csv
     -> infinite loop of JSON txns to Kafka topic credit_card_transactions
     -> amounts always < 100000, ids start with TXN

2. Engineer runs producer_fraud_transaction.py once
     -> one message amount >= 100001, id TXF...
     -> bronze -> silver -> gold.high_value_transactions_alert
     -> email_notifier_sink emails the customer (all emails currently the same Gmail)

3. Engineer runs producer_fraud_card.py once
     -> card_number forced to 5008514036965665
     -> if watchlist JSON for that PAN has been Autoloaded,
        gold.fraud_card_alert fires -> fraud email sink

4. fraud_watchlist_data_generator.py drips CSV rows as JSON into a volume;
     fraud_watchlist_bronze Auto Loader picks them up.

5. customers_historic.sql loads 1000 customers with transaction_limit=100000
     into Postgres; a (not-in-repo) bronze.customers ingest feeds
     customers_silver.py.

6. Dashboard SQL reads silver + gold tables for ops monitoring.

================================================================================
NOTABLE INCONSISTENCIES (EXPLAINED, NOT CHANGED)
================================================================================
- README refers to producer.py which does not exist.
- Three producers each regenerate CSVs, so concurrent runs race on those files.
- Producers strip fraud_score/fraud_reason; FraudEngine work never leaves Kafka.
- producer_normal overwrites generator amounts/ids.
- Secret clusters: kafka_producer/.env vs 02_Setup_Secret_Scope.py use
  different Confluent bootstrap hosts/keys.
- Several gold table comments are copy-pasted incorrectly.
- Filenames transaciton_* misspell "transaction".
- Dashboard watchlist status filter 'active' vs CSV 'ACTIVE'.
- Watchlist resume logic looks for prefix 'WL' but CSV uses 'wl'.
- Alert sinks call dbutils() as a function; may fail secret fetch.
- StatsSnapshot, serialize_json, clamp, weighted_choice, math import unused.
- customers.csv has no email/limit; Postgres SQL does.
